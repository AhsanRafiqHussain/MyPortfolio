A DBA in the Codebase: Using AI Without Letting It Drift

A process-focused reflection on crossing the database/application boundary with AI as an assistant, while keeping scope, judgment, and release responsibility human-led.

A database upgrade is rarely only a database change. Compatibility assumptions can be spread across application code, connection layers, ORM mappings, queries, configuration, and schema. At some point, doing the database work well meant looking beyond the server and into the codebase.

That is not always a comfortable boundary. Database specialists are often expected to advise from one side while application developers own the other. In this project, I needed to work across that boundary: use my DBA experience to identify upgrade risks, make carefully scoped code changes, test them in the context of the application, and prepare understandable changes for review.

AI made exploration faster. It did not make the work automatic.

My experience was that AI could be an exceptionally capable assistant. It helped me explore unfamiliar code and consider compatibility risks. But an open-ended instruction could also lead it beyond the task: proposing unrelated fixes, making changes that were not needed for the upgrade, or treating an unverified assumption as if it were established fact.

The lesson was not to avoid AI. It was to define how it could help before asking it to act.

Start with a working agreement

I established explicit rules for the work: what the upgrade covered, which actions were prohibited, and what required my review and permission. For example, AI could not delete code or make structural changes on its own. Changes had to be documented, understandable to a human reviewer, and consistent with the project's existing coding practices.

That agreement turned the prompt from a vague request to “fix the application” into a bounded assignment. It also gave me a way to say no when a suggestion, even a technically plausible one, was outside the agreed scope.

Map the database touchpoints before changing code

I began with discovery rather than edits. The first pass was to map where the application interacted with the database: query execution, data-access and ORM layers, connection and driver code, plus configuration and schema assumptions.

From there, I reviewed potential compatibility changes through a DBA's lens. A type conversion is not just a compile-time change if it can truncate data. A numeric-type change may affect precision or downstream reports. A query or driver adjustment needs to preserve the application's behavior, not simply satisfy a new compatibility check.

AI helped me explore and organize candidates. I still checked each finding against the actual code and the defined upgrade scope before deciding whether it belonged in the change set.

Keep scope creep visible

Code review can uncover real issues that are not part of the current upgrade. AI can surface those too. Finding a legitimate issue does not automatically make it safe to fold into a migration: combining unrelated work makes the change harder to review, test, and roll back.

I treated out-of-scope findings as separate follow-up items rather than quietly expanding the upgrade. That kept the work focused and made it easier for the right people to decide what to do next.

Testing and review remain human responsibilities

AI can help suggest test cases and rollout questions, but it cannot decide what evidence is sufficient for a release. I reviewed the changes, checked that they followed the application's conventions, and used build and application-level testing to evaluate behavior. When a failure appeared, I investigated whether it was caused by the upgrade or already existed in the environment, rather than assuming either answer.

Each change needed a clear reason and a record. The final merge should be reviewable by another person, and the rollout plan should account for verification and recovery—not just the code edit.

What I took away

This work did not turn a DBA into an autonomous application engineer, and it did not turn AI into the owner of a production change. It showed me that a database specialist can contribute more effectively when they follow the application's data path into the codebase and collaborate across traditional role boundaries.

AI expanded how quickly I could explore that unfamiliar territory. Scope rules, DBA judgment, testing, and human review kept the exploration useful. The strongest result was not “AI changed the code.” It was a controlled process in which the changes remained understandable, testable, and accountable.

If you work in infrastructure or databases and have hesitated to share how you learn across domains, I think that process is worth talking about. The tools matter; so do the boundaries we set around them.

In short: use AI to widen the investigation, not to widen the scope. Let expertise guide the changes, and let evidence—not confidence—guide the release.
