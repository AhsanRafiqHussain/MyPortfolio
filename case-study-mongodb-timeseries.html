Schema Design for Time-Series Data in MongoDB

A schema recommendation built for real IoT projects — sensor networks and a portable e-toilet monitoring system — tested, measured, and rebuilt over six months.

Platform MongoDB Domain IoT sensor telemetry Timeline Two schema generations, 6 months apart

Time-series data — immutable, high-volume, ordered by time, and read mostly in aggregate — is a well-known fit for MongoDB. Organizations from utility-grid monitors to server-monitoring tools lean on it for exactly this shape of data. The hard part was never "can MongoDB handle it." The hard part was designing a document structure that stayed maintainable once real sensors, real gaps in connectivity, and real schema changes showed up.

Generation 1: nested by design, brittle in practice

The first schema followed the textbook approach for high-resolution time-series in MongoDB: one document per day, per sensor, with nested sub-documents for every hour, then every minute, then every second — pre-allocated in advance so updates could target an exact path instead of appending.

It worked. It also came with a cost that only showed up after living with it:

  • Every day's document had to be pre-generated before data could land — an operational job in itself.
  • The structure was rigid: any change to what a sensor reported meant reworking the schema from scratch, and every application query written against it.
  • Analytics fields were baked into the nesting, which meant the document size and complexity scaled with granularity, not with actual data volume.

Generation 2: flatten, and let MongoDB do less pretending

After six months running the nested schema against live sensor data, the redesign kept the one thing that mattered — a document per day, per sensor — and removed almost everything else. No pre-generated hourly/minute/second skeleton. No baked-in aggregation hierarchy. Just a flat array of readings for the day, with a handful of pre-computed daily stats (max, min, count) at the top level.

✕ Gen 1 — nested per second
{ date, status, eui, ultrasonic: { hours: [ { 0: { dateHour, 0: {0:47,...,59:45, intervalSecond:{...}}, ... intervalMinute:{...} } }, ... × 24 hours ]}, load: { hours: [ ... ] } } — pre-generated daily, per sensor — any schema change = full rework — size scales with granularity
✓ Gen 2 — flat, per day
{ _id, date, status, operatingStatus, eui, battery, max_temp, min_temp, count, sensor_data: [ { temperature, payload, time }, { temperature, payload, door_status, time }, ... ] } — no pre-generation required — schema changes don't cascade — size scales with real readings

What the numbers said

Same local benchmark environment, comparing one full day of per-second event data against the redesigned per-day, per-sensor document:

MetricDocument-per-event (Gen 1 pattern)Document-per-day (Gen 2)
Create 1 day of data19.358 s1.467 s
Collection size (JSON)9,161 KB1,447 KB
Find time0.995 s0.145 s
Update — first second0.004 s0.019 s
Update — last second0.057 s0.042 s

The pattern holds at broader scale, too. Comparing document-per-event against document-per-minute aggregation on the same class of workload: 3,600 reads collapse to 60 for an hour of data, write operations drop from 60 individual inserts to 1 insert plus 59 targeted updates, and the _id index alone for a billion events shrinks from roughly 32 GB to roughly 0.5 GB. None of that is MongoDB getting faster — it's the document boundary doing less unnecessary work.

The actual fix wasn't a MongoDB feature. It was accepting that a schema optimized for theoretical query flexibility at every granularity was paying for that flexibility on every write, every day, whether or not anything ever queried at second-level resolution. Once daily and per-sensor was accepted as the real access pattern, the schema — and the ops burden of pre-generating it — got dramatically smaller.

Where this generalizes

The specific project was sensor telemetry for a portable e-toilet monitoring system and a broader IoT sensor network, but the underlying decision shows up anywhere high-frequency events get modeled in a document store: choose the coarsest grain that still serves your real query pattern, and let periodic aggregation — not nested pre-allocation — handle the rest.
