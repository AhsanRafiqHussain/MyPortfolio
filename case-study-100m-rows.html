The 100M Row Table Is Not Your Problem. Your Schema Is.

How schema design and data lifecycle management solve what indexing and partitioning can only patch — with real PostgreSQL benchmark numbers.

Platform PostgreSQL 15 (Supabase) Scale 5,000,000 rows Type Reproducible benchmark

I've been asked this question in interviews more times than I can count: "How would you optimize a table with 100 million records?" The expected answers come quickly — partitioning, indexing, materialized views, caching. Everyone in the room feels like the right things were said.

They're not wrong. They're just answering the wrong question.

The question assumes the problem is volume. It isn't. Volume is a symptom. The problem is a design that grew into a shape nobody planned for — and one day there are 100 million rows, the queries are slow, and someone calls it a performance problem. It's a design-debt problem coming due.

Two decisions, made on day one

There are two decisions that determine whether a table with millions of rows is a problem or just a fact of life. Neither is made by a DBA after the queries slow down — both are made by whoever designs the schema first.

1. Row width

Every byte stored unnecessarily on a row is a byte every query, scan, and vacuum reads for the rest of that table's life. The most common offender is denormalized customer data — when name, email, and phone repeat on every order row, you're not storing one customer record, you're storing it once per order, potentially millions of times.

2. Data lifecycle

Most tables don't need 100 million rows — they have that many because nobody decided what happens to old data. Partitioning by time isn't an optimization technique; it's an acknowledgment that data has a lifecycle. The query speed-up is a side effect of that decision, not the goal — which is why partitioning-for-performance and partitioning-for-lifecycle produce very different outcomes in practice.

The test

Two versions of an orders table, PostgreSQL 15, 5 million rows loaded into each. Same business data, same queries, different schema decisions.

✕ orders_bloated
order_id, order_date, status, customer_name, customer_email, customer_phone, ship_city, ship_country, product_sku, product_name, category, unit_price, quantity, total_amount, discount_code, notes — customer data repeats on every row — status overwritten, no history — no partitioning
✓ customers + orders_clean
customers( customer_id, name, email, phone) orders_clean( order_id, customer_id → FK, order_date, status, ship_city, ship_country, product_sku, unit_price, quantity, total_amount, discount_code ) PARTITION BY RANGE (order_date) — customer data stored once — narrow row, monthly partitions — old data dropped, not deleted

Same 5 million rows, same business data. A 43% difference in storage purely from not repeating customer data on every row — every scan on the lean schema reads 76% less than it needs to on the bloated one.

The date-range query came back 9× faster — not from any index or tuning, but because the partitioned table only touched the January 2024 partition (2,846 buffers) while the bloated table read the entire table (118,040 buffers) to answer the same question.

The lifecycle test is the one that makes the argument most clearly: deleting 3 months of old data from the bloated table took 35.7 seconds, scanned the entire table, and left 411,474 dead rows behind — space that doesn't return until autovacuum runs, which under production load could be hours. Dropping the three equivalent partitions from the clean table was instant. Zero dead rows. No vacuum required.

Five typical "optimization" indexes were added to the bloated table — date, status, email, SKU, country. Every single one showed zero scans. The table paid a write penalty on every insert and a storage cost of 329 MB for indexes that were never used once. That's not optimization. That's the appearance of effort with the cost of debt.

When 100 million rows is actually correct

Intellectual honesty requires saying this clearly: some tables should be large. An event log recording every state change, a telecom billing system with years of CDRs, a compliance table retaining data for seven years under regulatory requirement — these are large because the business requires it, not because nobody planned. If they're partitioned by time and archived on schedule from day one, their volume is a feature, not a failure.

The real question

Retrofitting a 100-million-row table is possible — but every technique is the expensive version of a decision someone should have made on day one. Designing it right from the start costs almost nothing: a partitioned table isn't harder to query, and separating customer data isn't significantly more complex to build against. Those are low-cost decisions at design time that become high-cost problems at scale.

Next time someone asks how to optimize a table with 100 million rows, ask a different question first: when was the schema last reviewed? That answer tells you more than any execution plan.
